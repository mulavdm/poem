# OKF Bundle Update Log

## 2026-07-23 (Windows scenarios self-provision, and the present channel is corrected)

- **Feature**: `launch` now supports `platform: "windows"` — an `exe`, an optional PowerShell `build`, and `prepare_window`. Verified from cold with the packaged build deleted and no process running: one command built the package, launched it, foregrounded the window, drove 480 frames, and captured. `reuse_running` defaults true on Windows, because starting a rival process that loses the race for the inspection port is worse than driving the one already there, and killing the user's window uninvited is worse still.
- **Bug fix**: `swapchain_->Present` was **inside** the `present` timing channel, while the GLES presenter had always excluded its `eglSwapBuffers`. The two platforms' headline native metric was therefore never measuring the same thing, which defeats the stated reason for sharing the recorder. `RendererD3D11::Present` is now separate from `Render`, so the channel covers geometry compilation and draw submission as documented.
- **Bug fix**: three defects the first Windows run exposed, each of which had been silently degrading results. Readiness treated "`/state` answers" as ready, but a freshly launched app serves `/state` before its first frame exists and the component tree is empty — readiness now requires a populated tree. Foregrounding round-trips through the native debug channel and the surface stops answering while that is in flight, so readiness is re-established after `prepare-window` instead of assumed. And a capture taken immediately after a click returned the *previous* frame, because a click returns when the engine accepts it, not when the frame is presented — captures now wait for the frame counter to advance, which is exact where a fixed sleep is a guess.
- **Bug fix**: scenarios now verify every component id against the live tree before driving. A leftover `adb forward` left the Android app on port 47831, so the Windows scenario "reused" it and failed with a bare `400 Bad Request` from inside a warmup. The check names the missing ids and says plainly that the app on the port may not be the one the scenario expects.
- **Outstanding, unexplained**: `native.present` p95 measures **5.4 ms** under `poemdrive` against 0.53 ms in earlier runs of the same scene at identical window geometry (1475x975, `window_foreground` false in both). Splitting `Present` out did not move it, so the compositor is not the cause. The 4.17 ms budget therefore fails, and the budget has deliberately **not** been relaxed to make it pass: the discrepancy is a measurement question, and tuning a threshold until it goes green would destroy the only signal that raised it.
- **Modified Concepts:** [windows-host.md](/concepts/architecture/windows-host.md) (why `Present` is separate from `Render`), [perf-profiling.md](/concepts/automation/perf-profiling.md) (Windows launch, the stronger readiness definition, target verification, and capture waiting for a new frame).

## 2026-07-23 (An Android scenario is one command from a cold machine)

- **Feature**: A scenario can now declare a `launch` block, and `cmd/poemdrive` performs the whole preamble: boot the configured AVD when no device is attached, build the APK if missing (`-build` forces it), install, set the inspection system property, restart the activity, forward the port, then drive. `-no-launch` drives something already running, and an attached device always wins so a physical phone is never displaced by an emulator. Verified from genuinely cold: emulator killed, app uninstalled, APK deleted — one command booted, built, installed, launched, measured, and captured.
- **Rationale**: the previous state claimed "one command" while six manual `adb` and build steps came first. A preamble a human has to remember is the difference between a scenario that is a fixture and one that is a suggestion; the interactions were pinned but the environment they assumed was not.
- **Two details found by getting them wrong**: the inspection property must be set **before** the process starts because `pkg/mobile` reads it at package init, so the order is setprop → force-stop → start; and `build_apk.sh` resolves its app-directory argument against the working directory, so the tool runs it from the script's own folder as its documented usage does, not from the repository root, which silently resolved the path elsewhere and failed the build.
- **Feature**: Added `scenes/baselines/` with the first recorded Android baseline and a README stating plainly that baselines are environment-specific — a reference for detecting that *this* environment got worse, not a threshold other machines must meet. It also records that the figures in `docs/M0_performance_baselines.md` predate the tool and are not comparable, having been reconstructed by polling `/perf/events` during the run.
- **Modified Concepts:** [perf-profiling.md](/concepts/automation/perf-profiling.md) (the `launch` block, its flags, and the two load-bearing ordering details), [overview.md](/concepts/automation/overview.md) (the manual `adb` enablement recipe now noted as the manual form, with the automated path beside it).

## 2026-07-23 (Android capture joins the inspection surface)

- **Feature**: The Android presenter now serves frame capture instead of refusing it. The request still arrives on the transport thread and `glReadPixels` still needs the GL context that only the render thread holds — so the request is **queued** to `DrawFrame` and awaited on a condition variable, rather than declared impossible. The readback happens before `eglSwapBuffers`, because the default `EGL_BUFFER_DESTROYED` swap leaves the back buffer undefined afterwards, and GL's bottom-up rows are flipped to the top-down RGBA the D3D11 host produces so callers cannot tell the platforms apart. The wait is bounded at 3s because a paused presenter draws no frames; timeouts and GL errors report themselves rather than returning a blank image. `captureDesktopFrame` stays unavailable — it needs MediaProjection consent an automated scenario cannot answer. Verified on the emulator: the preferences checkbox tick captures as two clean diagonal strokes, confirming the GLES line fix in presented pixels rather than by inference.
- **Feature**: `cmd/poemdrive` gained a `capture` step, so one scenario run yields both timings and images on either platform. Captures fire only on the final pass through the step list — repeating them every cycle rewrote the same filenames and charged every cycle for a readback and PNG encode, which measurably perturbed the measurement: `native.present` max fell from 6.5 ms to 2.0 ms once fixed. Added `scenes/android-preferences.json`, which drives the checkbox and captures both states.
- **Rationale**: the previous design told callers to run `adb shell screencap`. That pushed the work out of band into every caller, could not be driven by a scenario, and captured the *screen* rather than the presenter's own output — so the two platforms could not be compared, and Android could not be automated end to end.
- **Modified Concepts:** [android-presenter.md](/concepts/architecture/android-presenter.md) (capture implemented, the queueing mechanism, pre-swap readback, row flip, bounded wait, and why desktop capture stays out), [overview.md](/concepts/automation/overview.md) (platform-support matrix: capture endpoints now yes/yes with `/desktop-frame` the sole exception), [perf-profiling.md](/concepts/automation/perf-profiling.md) (the `capture` step, its sources, and why it runs only on the final cycle).

## 2026-07-23 (Scenario replay makes the perf gates repeatable)

- **Feature**: Added `cmd/poemdrive`, which replays a scenario file against a running app over the automation surface and gates the resulting timings against budgets and a recorded baseline. Nothing about any app is compiled in — the scenario supplies the base URL and the step list — so one binary drives the Windows gallery, MAPPS, or an Android device over `adb forward`. It decodes into `render.PerfState` and `render.NativePerfState` directly rather than redeclaring the JSON shapes, so a change to the perf contract breaks the build instead of silently mismeasuring. Percentiles come from the server-side ring rather than being reconstructed by polling `/perf/events`, which is both exact and free of the polling load that perturbed the original baseline measurements.
- **Feature**: Added `scenes/gallery-tabs.json` and `scenes/mapps-camera.json`, the fixtures `Plan.txt` referred to as "the defined gallery and MAPPS scenes" when no such definition existed. The MAPPS scene is a **balanced** zoom cycle returning to its starting zoom; the unbalanced version is why two earlier runs of that scene differed by ~50%, each drifting to a different zoom depth over different geometry. A scene that does not return to its starting state is not a fixture, and `cmd/poemdrive`'s tests validate the shipped scenes so a typo fails the build rather than producing a gate that measures the wrong thing.
- **Feature**: A regression must exceed an absolute floor as well as a percentage. Driving the real gallery exposed that two consecutive runs of an **unchanged** binary drift 19–35% at p95/p99 — not instability, but Go-side timings quantizing to ~0.5 ms on Windows against a p95 of ~0.55 ms, so one bucket reads as a third. With the floor, consecutive runs pass while a baseline doctored to represent a 4x regression still fails on six metrics. A budget naming a metric the run never produced also fails rather than passing quietly, since a `native.*` budget against a host with no native debug channel would otherwise succeed on absent data.
- **Modified Concepts:** [perf-profiling.md](/concepts/automation/perf-profiling.md) (new "Scenario replay" section covering the metric namespace, warmup-before-reset, and the three deliberate gate behaviours), [performance-benchmarks.md](/concepts/architecture/performance-benchmarks.md) (new "Pinned scenes" section, and why the MAPPS scene carries no budgets while its baseline sits 15–24x over the plan's target).

## 2026-07-23 (Measurable performance gates)

- **Feature**: Added native frame timing to the Windows host. Nothing in either C++ host timed frame CPU work — the only clocks present were for gestures, fling, and audio — so the migration plan's "native framework CPU work below 4.17 ms at p95" budget had **no measurement behind it at all**, and every figure POEM reported was Go-side. New `shared/poem/perf.{h,cpp}` retains raw samples per channel in a bounded ring and reduces them to percentiles on demand; `ScopedTimer` instruments `present` (geometry compilation plus draw submission on the UI thread, excluding GPU execution), `decode_frame`, `decode_map_scene`, and `apply_map_scene`. Pinned by a new `poem_perf` CTest target (7 cases: nearest-rank ranks, order independence, ring eviction, channel isolation, rejection of negative/non-finite samples, reset, empty). First measurement on the gallery tab-switch scene: `present` p95 0.95 ms against the 4.17 ms budget, but p99 11.1 ms and max 21.7 ms — the tail is where the risk is. **Modified Concepts:** [protocol.md](/concepts/protocol.md) (new "Native timing on the debug channel" section).
- **Feature**: Added percentiles to the Go frame tracker. `PerfFrameStats` previously exposed only running averages and a max, which **cannot answer a percentile gate**; the only raw per-frame data was the 256-entry event ring, shared with automation and event-batch entries, so it wrapped after roughly 128 driven interactions and had to be scraped by polling faster than it wrapped. A dedicated 4096-sample frame ring now backs `frames.percentiles`, reporting mean/p50/p95/p99/max for `total`, `build_pages`, `render_pipeline`, `serialize`, `write`, and `go_work` (build+render+serialize, the split the plan budgets separately from transport write). Each phase is ranked on its own ordering — a frame that is p95 for serialization need not be p95 for layout. Nearest-rank matches the native recorder's definition so the two sides of the boundary are comparable, and both contract tests assert the same ranks over 1..100.
- **Feature**: Frame `PerfEvent`s now carry `build_pages_ms`, `render_pipeline_ms`, `serialize_ms`, `write_ms`, and `command_count` as full-precision fields. The `details` string kept the same numbers but `%.2f`-formatted, quantizing every split to 0.01 ms — fine for reading, useless for regression detection.
- **Breaking change** (wire, inside v4): `NativeDebugRequest` appends a `resetPerf` flag and `NativeDebugResponse` appends a count-prefixed native-timing phase list, following the established append-inside-v4 rule used for fog and `ShadowCascades`. Host and application DLL already ship as a locked pair, so no tolerant-decode path was added; the decoder bounds the phase count against a malformed allocation. Round-trip coverage extended in the same change.
- **Feature**: New `GET /perf/native` returns the host's own timings, and `POST /perf/reset` now clears the native rings in the same call so a measurement scoped to one driven scene cannot blend with native samples from the previous one. Hosts without a native debug channel (web, test drivers) have nothing to clear and that is not an error. **Modified Concepts:** [perf-profiling.md](/concepts/automation/perf-profiling.md) (`frames.percentiles`, `/perf/native`, full-precision event fields, reset semantics), [endpoints.md](/concepts/automation/endpoints.md) (endpoint list).
- **Still open:** the gallery and MAPPS "scenes" the gates refer to exist only as ad-hoc driving loops, and MAPPS needs a fixed replayed camera path — successive zoom runs differ by ~50%, which swamps any regression a gate would catch. Android has no native debug channel, so its presenter remains untimed. Go-side timings on Windows appear quantized to ~0.5 ms steps, which is coarse against a 2.08 ms budget and wants confirming.

## 2026-07-23 (Line rendering and an Android transport spin)

- Fixed `DrawLine` on **both** presenters, which had diverged from each other and from the Go reference rasterizer (`automation.go`'s `drawLine`, which draws a true segment between the endpoints). D3D11 offset the endpoints along the segment normal but passed them to `AppendQuad`, which expands an *axis-aligned* extent into `(x1,y1)-(x2,y2)`: for a horizontal line the two offset endpoints share a Y and for a vertical line an X, so the quad collapsed to zero area and **every axis-aligned line rasterized nothing** — the datepicker's calendar icon (four strokes) was entirely invisible, and chart gridlines and fill columns with it. Diagonals produced two overlapping axis-aligned boxes shaded by an SDF rect that did not coincide with the emitted geometry, so the spinner rendered as scattered horizontal dashes. GLES had the complementary defect: it filled the axis-aligned bounding box, so axis-aligned lines were correct and every diagonal became a solid block. `AppendLineQuad` on both backends now pushes four explicit rotated corners. Because both fragment shaders shade `drawType 0` with an axis-aligned rounded-box SDF that cannot describe a rotated segment, the shading rect is padded 2px past the quad's bounds so every rasterized fragment shades solid and the geometry alone defines the line; the cost is hard rather than SDF-antialiased edges, which a proper capsule SDF would restore at the price of a shader and vertex-format change on both backends. Verified on Windows by A/B frame capture through the HTTP automation surface (`/self-frame`) at baseline and with the fix: the calendar icon goes from nothing to four strokes, and the spinner from scattered dashes to a clean 10-spoke radial burst. **The GLES half is compile-checked only and still needs an emulator pass.**
- Fixed the Android host's transport thread spinning at 100% instead of shutting down. `ReadExact` (`android_engine/src/main.cpp`) returned false only on `n < 0`, so a zero-length read — the engine closing its end — looped forever rather than terminating the transport. It now fails on `n <= 0`, matching the Windows host's `NativeApp::ReadExact`, which already rejected `count <= 0` for the same reason. Untested on device.
- Ignored the two packaging output directories that the documented build recipes produce but `.gitignore` did not cover: `/dist/` (`windows_host/build.ps1` — portable bundle, ZIP, MSIX) and `android_engine/build/` (`build_apk.sh` — per-ABI `apkroot`, `.apk`, `.so`). Neither had tracked files.
- **Correction (2026-07-23).** This entry originally closed with "no concept doc referenced `DrawLine` semantics, so nothing under `okf/concepts/` needed updating" — which inverts the parity rule. A rule that no concept documents is a gap to fill, not a reason to skip the update, and the ledger records what changed in the bundle, so an entry naming no concepts is a sign the middle step was missed. Reconciled now: **Modified Concepts:** [windows-host.md](/concepts/architecture/windows-host.md) (the rotated line-quad rule, why offsetting endpoints into the axis-aligned `AppendQuad` collapses to zero area for every horizontal and vertical line, and why the shading rect is padded past the quad's bounds), [android-presenter.md](/concepts/architecture/android-presenter.md) (a zero-length `PoemHostRead` terminates the transport rather than spinning it, and why the two hosts must agree on what end-of-stream looks like). The GLES half of the line rule had already reached `android-presenter.md` through the reconciliation entry above; the Windows half — the more severe defect — had not.

## 2026-07-22 (Overlay primitive and a responsive map canvas)

- Added `OverlayNode`, a twentieth `Node` kind, and its `render.Overlay` component (`pkg/render/layout/overlay.go`). It z-stacks floating layers over a base within one box: the base fills the box and alone sets the measured size, while each layer is sized to itself and pinned to one of nine anchors, `Inset` logical pixels clear of the edges it hugs. Layers paint last-on-top and are hit-tested before the base, so a floating control wins the pointer over the canvas beneath it and a miss falls through. It is wired through every node-tree consumer — `LowerSemantic`, the native and web `render.go`, `collectMapNodes`/`currentMapSource`, and design-lint — so a map nested under floating controls is still found and linted. Unlike `ModalNode` it is non-modal and leaves the base interactive. **Modified Concepts:** [overview.md](/concepts/app/overview.md) (node count nineteen → twenty), [desktop-driver.md](/concepts/app/desktop-driver.md) (new `OverlayNode` section distinguishing it from the modal overlay system).
- Fixed the same **"layout output mistaken for author intent" anti-pattern** (`UI101`) across three components. `Button` and `Badge` measured from their stale laid-out `Rect`, so after a resize they froze at their first-laid-out width and truncated their labels; they now size from label content (`Button` gains an explicit `FixedWidth` for genuine author sizing, distinct from the laid-out bounds). The map viewport (`ImageViewportNode`) had the same defect and now **fills its container** rather than feeding its laid-out `Rect` back as an explicit size — so it tracks window resizes instead of freezing, and a map canvas that hosts corner overlay controls fits the viewport, keeping those controls reachable.
- Gave cartography its **own theme tokens** (`theme.Colors.Cartography`: water, waterway, land, building, road) rather than borrowing the UI `Accent` for water. A saturated accent-blue canvas read as an interactive surface; the calm desaturated blues recede so the map reads as a rendered surface, not a control — the interaction side of "Data Canvases Are Not Controls". Light, dark, and high-contrast variants each define the set.
- Collapse **tile-seam duplicate labels** by proximity (`pkg/cartography/labels.go`). A named feature spanning a tile seam emits one candidate per tile at slightly different world points, so their collision boxes never overlap and every copy places — "Oosterdok" rendered four times over one dock. A later candidate of identical text within 320 logical px of an already-placed one is now dropped (highest-priority instance wins, since placement runs in priority-then-ID order); the same name genuinely far away is beyond the radius and still labelled.
- **Documentation reconciliation.** The M9 GPU cartography subsystem had shipped across many commits with no concept doc — only the transport lived in `protocol.md` — and several concept docs had drifted from the code (some with newer bodies but stale timestamps). **Added Concept:** [map-rendering.md](/concepts/architecture/map-rendering.md), covering the `pkg/cartography` pipeline (decode → style → scene → declutter → labels → sun), the shared `shared/poem/*.h` projection/lighting/shadow maths, the GPU depth path (hi/lo camera split, "bigger = closer" depth, `ddx/ddy` normals), and the fog/shadow-cascade/marker-billboard/POI-category layers. **Modified Concepts:** [protocol.md](/concepts/protocol.md) (fog and `ShadowCascades` appended inside v4, POI category in the vertex tail), [adaptive-design.md](/concepts/app/adaptive-design.md) (`ActionNode` selected state, semantic `Empty`, `UI072`/`UI073`), [overview.md](/concepts/app/overview.md) + [desktop-driver.md](/concepts/app/desktop-driver.md) (`OverlayNode`), [component-parity.md](/concepts/app/component-parity.md) (`MapViewportNode`, `OverlayNode` rows), [web-backend.md](/concepts/app/web-backend.md) (the vector map viewport via canvas + WebGL2/WASM), [windows-host.md](/concepts/architecture/windows-host.md) (DXGI flip-discard presentation), and [layout-measurement.md](/concepts/architecture/layout-measurement.md) (the `UI101` measurement anti-pattern). Stale timestamps on the edited docs were brought current.

## 2026-07-21 (M9 cache policy and clearing)

- `MapCachePolicy` now governs the resource cache instead of being decoded and ignored. **Memory Only** writes nothing to disk and, when switched to, clears what earlier policies persisted — a setting that left a copy behind would not be the setting the user asked for. **Persistent Online Only** persists as an accelerator: an unreachable provider stays an error. **Persistent Offline** additionally answers from verified disk copies when the provider cannot, which is what keeps the map drawing with no connection. ## 2026-07-21 (shadow cascades — workstream C complete)

- Buildings now **cast sun shadows** onto the street and onto each other. Each cascade is a depth-only pass rendered from the sun's point of view into a 1024² depth map; the main pass projects each fragment into the same light space and compares. Cascade count is **driven by the quality tier** — Battery Saver 0, Balanced 1, High 2 — carried on a new `MapSceneDelta.ShadowCascades` field appended after the fog fields, so existing protocol values keep their positions.
- Shared, as with everything else in the GPU path: `mapgpu::MakeShadowSetup` builds the orthonormal light frame and cascade extents, `MapLightCoord`/`MapCascadeRadius`/`MapShadowFactor` join the canonical shader source, and the uniform block carries the frame. Each presenter contributes only its render-target plumbing. Cascades are **concentric on the camera**, which keeps them stable as the view pans: geometry slides through a fixed frame instead of the frame chasing the camera and shimmering. Only extrusions cast (ground casting onto itself is pure acne); ground and extrusions both receive. Shadowed surfaces darken by a strength factor rather than to black, so facades stay readable.
- Note the two opposing depth conventions, which is why they are separate states: the main map pass is "bigger is closer" (GREATER_EQUAL, cleared to 0) while the shadow pass is conventional "nearer to the light is smaller" (LESS, cleared to 1).
- **Verified by measurement, not by eye.** A first look suggested the scene was uniformly darker, but an A/B pixel diff against a cascades-off build showed *zero* difference — shadows were not applying at all. The cause was plumbing, not maths: `shadowCascades` was decoded from the protocol but never retained on the scene, never copied in `ApplyMapScene`, and never passed into the `Lighting` aggregate, so the count silently defaulted to 0. After fixing all three, the diff showed thin slivers (0.2% of pixels) — correct, but a high midday sun casts almost nothing. Forcing a 05:30 sun produced long directional shadows over **17.2%** of pixels. The eye would have accepted the broken build; the diff would not.

## 2026-07-21 (depth-tested markers)

- POI markers now draw in the GPU depth pass as **billboards**: the world position is projected on the GPU so the marker is depth-tested against buildings, then the quad corner is offset in screen space so markers keep a constant on-screen size. A POI behind a building is now hidden by it instead of floating over the skyline — the remaining half of the "dots all around" problem. Markers **read depth but do not write it**, so they never occlude one another, and a small depth lift keeps them off the ground plane they sit on.
- Expansion is shared, not per-backend: `mapgpu::AppendMarkerVertices` turns a point batch into two triangles per marker, reading radius from the cartography vertex `width` field (floored at `kMinMarkerRadius`), and `mapgpu::ReadSourceVertex` is the one decoder for that layout. `MapMarkerClip`/`MapMarkerAlpha` join the canonical shader source, so both presenters get identical placement, sizing and the soft round edge. Each backend contributes only its entry points and buffer upload.
- Contract tests cover the expansion (corner coverage, radius floor, elevation and colour carried through) and its bounds safety: an out-of-range index or a count past the index buffer is skipped rather than read out of bounds, since these buffers originate in decoded MVT.
- Markers left the CPU composite entirely; it now carries only lines and textured label quads. Labels stay unoccluded on purpose — legibility beats strict correctness for text, which is also how MapLibre and Google Maps behave.

## 2026-07-21 (GPU depth map path, de-duplicated across backends)

- Map ground and building extrusions are now **projected on the GPU and depth-tested** instead of being flattened to 2D on the CPU and painter-sorted. Buildings occlude correctly by construction: the earlier translucent, interpenetrating blocks are gone, replaced by solid silhouettes with correct water/building layering. Confirmed by sight on Android (GLES) and Windows (D3D11).
- **The maths is written once.** `shared/poem/map_shader.h` holds the canonical shader body (`MapLocal`, `MapDepth`, `MapClip`, `MapShade`, `MapFog`) with two small dialect preludes; each backend supplies only its entry points, which are the irreducible part (HLSL semantics/cbuffers vs GLSL attribute/varying/uniforms). `shared/poem/map_gpu.h` owns the uniform packing (`MakeUniforms`) and batch selection (`IsGpuBatch`, `HasGpuBatches`), so neither presenter re-derives them. This replaced a third and fourth copy of the projection/lighting/fog formulas that had been hand-transcribed into HLSL and GLSL — precisely the divergence the shared module was extracted to prevent. New contract tests pin the uniform packing (including that the hi/lo camera split recombines to double precision) and the batch filter.
- Two details worth recording: the camera centre must be **split hi/lo** because mercator coordinates at city zoom lose metre-scale bits in single precision on the GPU; and depth is normalised over the full `[-19d, +d]` range the perspective divide can produce, since a naive mapping saturates into z-ties. Depth convention is "bigger = closer" (GREATER_EQUAL, cleared to 0), which lets equal-depth ground layers resolve by draw order exactly as the flat path did.
- **GPU-only for map geometry, by design.** The CPU painter path cannot carry tens of thousands of reprojected triangles per frame on mobile, so it is no longer a fallback for ground/extrusions: the Android host negotiates a GLES3 context (derivatives and 32-bit indices are core there) and a shader failure is reported rather than silently degraded. The CPU composite still carries dots, lines and textured label quads on top.

## 2026-07-20 (D3D11 GPU map path: vertex-shader projection + real depth buffer)

- The Windows presenter now draws map ground and extrusions on the GPU: a dedicated shader pair projects the raw cartography vertices (world mercator x/y, elevation metres) exactly as `shared/poem/map_view.h` does, with the camera centre split hi/lo for float precision, and lighting/fog moved into the pixel shader — per-face normals recovered from `ddx/ddy` of the local-position varying (the derivative of a linear varying is the true face plane), fog constants passed from the shared header via cbuffer so HLSL hard-codes nothing. ## 2026-07-20 (Windows host startup deadlock fixed)

- The Windows host published semantic trees with a **synchronous** `SendMessageW` from its engine-reader thread, while every other engine message used `PostMessageW`. That blocked the reader until the UI thread replied — but the UI thread could be inside `SendEvent` → `WriteMessage`, waiting on an engine that could not drain because the reader was the only thing draining it. The resulting three-way deadlock left the window blank and unresponsive immediately after startup (main thread reached its message loop, then stalled on the first `WM_SIZE`). It reproduced on MAPPS but not the counter example, because a semantics-rich UI wins the race. `WM_POEM_SEMANTICS` already takes ownership of the heap-allocated tree, so the fix is to post it (freeing it only if the post fails). Verified with `SendMessageTimeout`: before `pumping=False hung=True`, after `pumping=True hung=False`, and the app now renders its full UI and vector map. This also unblocked visual confirmation of the D3D11 sun-lit extrusions (pitched Amsterdam: dark wall faces against lit roofs), so both native presenters are now confirmed by sight, not just by construction.

## 2026-07-12 (tabs controlled selection)

- Fixed `components.Tabs` ignoring application-driven selection changes when **controlled**. `activeIndex` preferred the roving position stored in `TransientState` over `SelectedID` unconditionally, so once a user had clicked any tab, an application that later set `SelectedID` itself — without a click or keypress — was silently overridden by the stale roving position. That defeats the entire point of a controlled component: an app cannot programmatically move the selection (a "jump to this tab after saving" flow). `tabsInteraction` now also snapshots the application's `SelectedID` at the moment a roving position is stored, so `activeIndex` can tell "the application moved the selection" (snapshot differs from the current `SelectedID` → adopt it and resync the snapshot) from "the user roved" (snapshot matches → keep the roving position). The resync matters: without it, an application changing back to a previously snapshotted value would look unchanged and be shadowed again. Uncontrolled `Tabs` are unaffected. Added a regression test covering click-then-apply and application-driven change; the existing roving-survives-rebuild test still passes unchanged. Unblocked the sibling Trellis project's `TabsNode`, whose selection is application-owned.

## 2026-07-12 (accordion uncontrolled persistence)

- `components.Accordion` now persists **uncontrolled** expansion (`OnToggle == nil`) in the `ApplicationState` transient store, keyed by `CompID`, instead of only mutating the instance's `Expanded` map. Previously an uncontrolled accordion rebuilt from scratch each frame — which is how `BuildPagesFn` and the downstream Trellis runtime both drive rendering — silently dropped every toggle, because the mutated map was discarded on the next rebuild. It now hydrates `Expanded` from the transient store (seeded from the author's initial open set on first sight) at each state-aware entry point and writes back on toggle, exactly how `Tabs` selection and `Select` popups already survive rebuilds. Controlled accordions (`OnToggle` set) are unchanged — the application still owns their `Expanded` map. Added rebuild-persistence and default-open-seeding regression tests; all existing accordion tests still pass. This unblocked the sibling Trellis project's `AccordionNode` (backend-local expand/collapse chrome, no `App[S]` involvement).
